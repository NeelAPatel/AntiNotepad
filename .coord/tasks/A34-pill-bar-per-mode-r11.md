## Do
1. **New `UI/PadBar.cs`: `internal sealed class PadBar`**, one bottom bar for one pane. It owns the three containers (the `Border`s `_barLeft`, `_barCenter`, `_barRight` and the Grid and root Border that `UI/PadWindow.Bar.cs` holds today) and exposes `Root` (the control the window places) plus `Pane` (a small enum `BarPane { Left, Right }`, Left is the only one used today).
2. **Items registry.** A container holds an ordered list of `BarItem` (record: `Id`, `Container` {Left, Center, Right}, `Order`, a `Control`, and optional `IsVisible(BarContext)` and `IsEnabled(BarContext)` predicates). Delete, the pager bar and New note are registered as items; the bar lays items out from the registry (sorted by container then order). Adding a control later is "register one more `BarItem`". Keep it small: no plugin system, no dependency injection. A fake item added in a selftest must appear in its container in order.
3. **`BarContext` record** (what the bar needs, nothing read from `PadWindow._active` inside `PadBar`): view kind (stack or slot n), the other pane's slot (for the marked second current dot), stack count and current index, is-blank flags, toggles (`ShowDeleteButton`, `ShowNewNoteButton`, `SlotDots`), bar style (docked, overlay, float), palette, and display strings for tooltips (labels from the shortcut map passed in as a lookup). `DecideBar` becomes a method of or next to this context (keep its tested behavior).
4. **Actions** passed in as a `BarActions` record of delegates (Delete, NewNote, Previous, Next, OpenSearch, SelectSlot(int)). `PadBar` calls them; it knows nothing about `Navigate`, `DeleteCurrent`, `_active` or the debounce (the debounce wrapper stays in `PadWindow` and is passed as the Delete action).
5. **Window side** (`UI/PadWindow.Bar.cs`, `UI/PadWindow.Layout.cs`, `UI/PadWindow.TopBlur.cs`, `UI/PadWindow.Keys.cs`): `PadWindow` keeps `List<PadBar> _bars` (one bar today) in place of `_bar`/`_barLeft`/`_barCenter`/`_barRight`/`_deleteButton`/`_newButton`; building the context from `_active` and settings happens in one `BarContextFor(pane)` method; `UpdateChrome`, `ApplyBars` (Docked, Overlay and Float parenting), `FloatPager`, `FadeChrome`, `SleepChrome`, `BarsSleepTick`, the overlay hide/show and the popup blur visual iterate the bars instead of one `_bar` (with one bar the result is identical). The swap button and `SwapView` take a pane argument (only Left is passed). Placement must work for more than one bar (stack them horizontally in the same layer or popup); only one is created today.
6. **Geometry in one place:** all bar sizing that `ConfigureBarStyle`/`BuildPill` compute stays in `PadBar` with the same `ChromeTokens`; no new literals.
7. **Selftests (small, `SelfTest/Bar.cs`, update `SelfTest/UI.cs` reflection and contracts where fields moved):** registry order and visibility (a fake item), context-to-content table (the existing `DecideBar` checks, moved if needed), a second `PadBar` can be created and parented without touching the first, actions are invoked through the record (a fake action sees a Delete click). Existing bar, fade and hit-test checks must keep passing against the new structure.
8. Comments and summaries per `.claude/rules/coding.md` on every new type and method; file header on `PadBar.cs`.
