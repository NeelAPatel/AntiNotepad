# A34-pill-bar-per-mode lens review

## Findings (proven)
1. [major] `product/AntiNotepad/UI/PadWindow.Bar.cs:30` - The r11 snapshot eagerly resolves all nine slot titles even when the bar displays the stack. This adds synchronous body reads and title parsing to stack navigation and to hiding with an overlay open. Exact path: `HideResident` (`UI/PadWindow.cs:266`) calls `CloseOverlay`; with an overlay present, `CloseOverlay` (`UI/PadWindow.Keys.cs:171`) calls `UpdateChrome`; its bar update (`UI/PadWindow.Layout.cs:326`) builds this snapshot. `Note.Title` (`Model/Note.cs:158`) computes a missing `TitleCache` through `PeekText`, whose unloaded-body path calls `ReadBody` (`:61-75`); `Store.ReadBody` (`Model/Store.cs:76-81`) performs `File.ReadAllText` synchronously. Before r11, `BuildPill` only requested titles for filled slots when actually rendering slot dots. A disposable hidden-window probe against the compiled product, with stack view selected and nine unloaded, uncached 1 MB slot bodies, measured `STACK UpdateChrome: bodyReads=9 elapsedMs=19.39 viewSlot=0`; a second cached refresh measured `bodyReads=0 elapsedMs=0.61`. Opening the actual Help overlay, clearing the title caches, then invoking its real close path measured `HIDE CloseOverlay prefix: bodyReads=9 elapsedMs=37.90`. These are fixture timings, not end-to-end hotkey latency, but the added UI-thread reads are proven. Smallest fix: retain the snapshot structure while resolving titles only for filled slots when slot content is displayed; stack contexts and empty slots should not request `Note.Title`. Add a small regression check that a stack bar refresh does not load unrelated slot bodies. This violates the no-slowdown constraint and r11's pure-refactor promise.
